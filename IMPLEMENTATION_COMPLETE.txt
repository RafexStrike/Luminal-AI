ARCHITECTURE PRINCIPLES
================================================================================

1. STATELESSNESS HANDLING
   Problem: HuggingFace has no memory
   Solution: Send full conversation history with each request
   Result: Model appears context-aware

2. CONTEXT REBUILDING
   Every request:
   ├─ Load message history from MongoDB
   ├─ Filter out system message
   ├─ Append new user message
   ├─ Send full array to HuggingFace
   └─ Save response to MongoDB

3. MESSAGE ORDERING
   ├─ sequenceNumber auto-increments per chatId
   ├─ System message = 0
   ├─ User/assistant = 1+
   ├─ Always load with ORDER BY sequenceNumber
   └─ Handles race conditions correctly

4. USER ISOLATION
   ├─ userId on every insert
   ├─ userId filter on every query
   ├─ No cross-user data access
   └─ GDPR compliant

COMMON QUESTIONS
================================================================================

Q: Why rebuild context on each request?
A: HuggingFace is stateless. Without this, model wouldn't see previous
   messages. This is the only way to achieve context-awareness.

Q: Why not store messages in the chat document array?
A: Individual messages allow better querying, editing, deletion, and
   searching. Also prevents document size limits.

Q: Why sequenceNumber?
A: Ensures messages are always in chronological order even if database
   inserts happen out of order (race conditions).

Q: Can multiple users use this?
A: Yes, userId filter on all queries ensures isolation.

Q: How much does it cost?
A: More than single-message APIs because context grows with conversation.
   Long conversations can be optimized with message summarization (future).

Q: Will this work with other LLM providers?
A: Yes, the context-building logic is provider-agnostic. Already set up
   for OpenAI and Groq as well.

Q: Can I run this on multiple servers?
A: Yes, MongoDB is the source of truth. No in-memory state to sync.
