## Executive Summary

### Overview

The **Flashcard Generation and Spaced Repetition Scheduling System** is a comprehensive, scientifically-grounded learning platform that automatically generates high-quality flashcards from educational conversations and intelligently schedules their review using a modern spaced repetition algorithm.

Unlike simple flashcard applications that require manual card creation, Luminal AI extracts question-answer pairs directly from tutor-student conversations, grades them by difficulty, and automatically schedules reviews based on the **Free Spaced Repetition System (FSRS- Lite)** algorithm—a sophisticated scheduler rooted in cognitive psychology and neuroscience research.

### Innovation Highlights

- **Automatic Q&A Extraction:** LLM-powered generation from unstructured conversations
- **FSRS-Lite Algorithm:** Deterministic, science-backed scheduler that adapts to individual learning curves
- **Difficulty Calibration:** Cards dynamically ranked and re-ranked based on user performance
- **Adaptive Intervals:** Review schedules adapt in real-time as cards are reviewed
- **Retention Targeting:** Configurable target retention rate (e.g., 90% recall probability)
- **Seamless Integration:** Automatic embedding and RAG indexing for retrieval-augmented study

## Problem Statement & Motivation

### The Gap Between Learning and Retention

The most significant barrier to educational success is not *understanding* but *remembering*. Research consistently shows:

1. **The Forgetting Curve (Ebbinghaus, 1885):** Without reinforcement, humans forget ~50% of learned material within 24 hours, 70% within 7 days, and 90% within 30 days.

2. **Passive Learning Failure:** Reading explanations (even excellent ones) is insufficient for long-term retention. Retrieval practice—actively retrieving information from memory—is essential for durable learning.

3. **Manual Flashcard Creation Barrier:** Even motivated students find it prohibitively time-consuming to create high-quality flashcards from lectures and readings. One hour of content typically requires 30-60 minutes to convert into 20-40 cards.

4. **Suboptimal Review Scheduling:** Most students either:
   - Don't use spaced repetition at all (review randomly or once)
   - Use naive spacing (fixed intervals like 1, 3, 7, 30 days) that wastes reviews on well-learned material
   - Use poorly-tuned algorithms (Anki's default settings aren't universally optimal)

### Challenges in Current Educational Systems

#### Challenge 1: Disconnection Between Explanation and Practice

Traditional AI tutoring systems typically follow this flow:

```
Student: "How does gradient descent work?"
           ↓
AI Tutor: [Provides 500-word explanation with examples]
           ↓
Student: "Got it, thanks!"
           ↓
[Conversation ends. Knowledge not reinforced. Forgetting curve activates.]
```

**Problem:** The tutor provides excellent explanation but provides zero mechanism for memory reinforcement. The student leaves the conversation with temporary understanding but long-term forgetting guaranteed.

#### Challenge 2: Time Bottleneck in Card Creation

Consider a typical student workflow with a traditional SRS:

1. Student completes tutoring session (1 hour) → 2,000 tokens of conversation
2. Manually identifies key concepts (15 min)
3. Creates Q&A cards (45 min)
4. Adds tags and difficulty ratings (15 min)
5. Uploads to Anki or Quizlet (5 min)

**Total time investment:** 80 minutes to process 1 hour of content

**Result:** Only 40% of students follow through (motivation drops with tedious manual work)

#### Challenge 3: Suboptimal Scheduling in Traditional SRS

Most flashcard systems use fixed interval schedules:

```
Review 1: Tomorrow (1 day)
Review 2: 3 days later (total: 4 days)
Review 3: 7 days later (total: 11 days)
Review 4: 14 days later (total: 25 days)
Review 5: 30 days later (total: 55 days)
[etc.]
```

**Problem:** This ignores individual difficulty, stability, and retention targets:
- Easy material (e.g., "What is the capital of France?") should be reviewed less frequently
- Hard material (e.g., mathematical derivations) needs more frequent review
- A student targeting 99% retention needs different intervals than one targeting 70%
- A concept learned 10 years ago doesn't need the same schedule as one learned yesterday

#### Challenge 4: No Integration of Performance Feedback

Manually-created cards provide no mechanism for:
- Tracking why specific cards are hard or easy for a student
- Ranking cards by efficacy (which cards teach best?)
- Identifying knowledge gaps (which topics is the student struggling with?)
- Auto-correcting card quality (poorly-worded cards that confuse students)

### The Solution: Integrated Flashcard + FSRS System

Luminal AI's approach solves these challenges through:

1. **Automatic Card Generation:** LLM-powered extraction transforms conversations → structured Q&A pairs instantly
2. **Smart Difficulty Classification:** Initial difficulty estimated based on content complexity; refined through user performance
3. **FSRS-Lite Algorithm:** Scientifically-grounded scheduling that adapts to each learner's profile
4. **Retention Targeting:** Configurable goals (e.g., "I want 90% recall probability for anything I study")
5. **Seamless Integration:** Cards automatically embedded, indexed, and queryable through RAG system

### Research Motivation

This system is grounded in extensive learning science research:

#### Core Research Foundations

**1. Spacing Effect (Cepeda et al., 2006)**
- Distributed practice (studying same material over time) vastly outperforms massed practice
- Optimal spacing increases retention by 200-300%
- Effect holds across ages, materials, and learning contexts

**2. Testing Effect (Roediger & Butler, 2011)**
- Retrieval practice (taking tests, interactive quizzes) improves memory more than restudy
- Effect compounds: repeated retrieval strengthens memory traces exponentially
- Difficulty of retrieval during testing predicts durability (generation effect)

**3. Desirable Difficulties (Bjork & Bjork, 1994)**
- Learning requires cognitive challenge—too easy = no reinforcement, too hard = discouragement
- Optimal spacing creates "desirable difficulty" where retrieval is challenging but possible
- Individual spacing must adapt to personal knowledge state

**4. Exponential Decay (Ebbinghaus, 1885; Wixted, 2004)**
- Forgetting doesn't occur linearly—it follows an exponential decay curve
- $R(t) = e^{-t/S}$ where R is retrievability, t is time, S is "stability" (strength)
- Modern SRS schedulers use this model to predict optimal review timing

**5. Difficulty as Independent Dimension (SM-2 Algorithm, Wozniak, 1990; FSRS, Jarrett, 2020)**
- Card difficulty and memory stability are independent factors
- Difficulty captures inherent "hardness" of material
- Stability captures strength of current memory trace
- Both must be tracked and updated separately

## Literature Review & Academic Foundations

### Spaced Repetition Systems: Historical Context

#### First Generation: Primitive Spacing

**Leitner System (1972):**
- Physical box with 5 dividers (labeled with fixed intervals)
- Card in divider 1 → review daily
- Card in divider 2 → review weekly
- etc.
- **Pros:** Simple, no technology needed
- **Cons:** Fixed intervals ignore difficulty, no personalization, no retention targeting

#### Second Generation: Basic Algorithms

**SM-2 Algorithm (Wozniak, 1990):**
- First computerized SRS
- Uses "easiness factor" (1.3-2.5) to adjust intervals
- Formula: $I_n = I_{n-1} \cdot EF$ where $I_n$ is the nth interval
- Popularity: Anki (modern SRS) uses SM-2 by default
- **Limitation:** Empirically tuned on limited data; hardcoded constants don't adapt to individual learners

**SuperMemo Algorithm (various versions):**
- SM-5, SM-6, SM-8, SM-11, SM-15, SM-17
- Increasingly complex, attempting to capture more learning dynamics
- **Challenge:** Each iteration adds parameters but marginal improvements diminish
- **Criticism:** Some users report SM-17 overcomplicates without significant benefit

#### Third Generation: Modern, Science-Based Algorithms

**FSRS (Free Spaced Repetition Scheduler, 2020-Present):**
- Developed by Jarrett Ye and open-source community
- Grounded in exponential forgetting curve: $R(t) = e^{-t/S}$
- Two independent factors: **Difficulty** (D) and **Stability** (S)
- Machine-learning calibrated using data from thousands of learners
- **Innovation:** Targets desired retention rate (e.g., "I want 90% recall probability")

**Research Supporting FSRS vs. SM-2:**
- Comparison study (Ye, 2021): FSRS achieves 90% target retention with 20-30% fewer reviews vs. SM-2
- Generalization: FSRS parameters work well across learner populations without retuning

### Flashcard Generation & Content Structure

#### LLM-Based Question Generation

**Recent Research:**
- Zhang et al. (2023) - "Learning to Generate Questions for Educational Content"
- Bao et al. (2023) - "Automatic Question Generation using Transformers"
- Findings: Modern LLMs (GPT-3.5+, Llama 2) generate pedagogically-sound Q&A pairs at 85-95% quality rate
- Key insight: Prompting strategy matters significantly - clear exemplars + constraints improve quality

**Quality Metrics for Generated Cards:**
1. **Clarity:** Is the question unambiguous? (target: >90% clarity)
2. **Scope:** Does it test one specific concept? (target: >85% single-concept)
3. **Answer Completeness:** Does the answer fully address the question? (target: >90%)
4. **Pedagogical Value:** Does answering the question demonstrate understanding? (target: >80%)

#### Difficulty Estimation from Content

**Automatic Difficulty Assessment Methods:**
1. **Lexical Complexity:** Flesch-Kincaid reading level, vocabulary frequency
2. **Conceptual Dependency:** Questions requiring integration of multiple concepts = harder
3. **Proof/Derivation vs. Recall:** Questions requiring derivation > recall questions
4. **Bloom's Taxonomy:** Remember < Understand < Apply < Analyze < Evaluate < Create

**Our Approach:** Multi-factor heuristic combining lexical + conceptual features + LLM rating

#### Extraction from Conversational Context

**Key Challenge:** Not all content in a tutoring conversation forms good flashcards.

**Example of Bad Flashcard:**
```
Q: "So like, if we have a function...?"
A: "Yeah, that's the limit definition."
```
**Problem:** Vague question, incomplete answer, informal

**Our Solution:** LLM uses context-aware extraction:
- Filters out questions/answers with low information density
- Rewords informal language into precise academic terms
- Checks for completeness (if a question is left unanswered, it's excluded or placed in "open questions")

### Adaptive Scheduling & Personalization

#### Individual Differences in Learning

Research shows significant variation in:
- **Learning speed:** Some people memorize in 2-3 reviews, others need 8-10
- **Forgetting rate:** Stability (S) varies from 1-200 days for learners with similar abilities
- **Difficulty perception:** Same card is "easy" for expert, "hard" for novice

**Implication:** One-size-fits-all interval schedules suboptimal.

#### Personalization Strategies

**1. Retention Rate as Meta-Parameter:**
- Different learners have different retention needs
- Medical student: "I want 99% retention (life-critical knowledge)"
- Casual language learner: "70% is fine (good enough for movies)"
- FSRS naturally supports this via target retention parameter

**2. Historical Performance Integration:**
- Stability (S) parameter captures "how strong is this memory?"
- Updated after each review based on user's actual performance
- Users who consistently report "Good" see longer intervals; users reporting "Again" see shorter intervals

**3. Difficulty Adaptation:**
- Initial difficulty estimated from content
- Updated after each review to reflect "is this actually hard for THIS learner?"
- Allows for personalization: same card may be easy for expert, hard for novice

### Integration with Cognitive Load Theory

**Cognitive Load Theory (Sweller, 1988):**
- Working memory has limited capacity (~7±2 items)
- Instructional design should minimize extraneous load and optimize germane load
- Flashcards + spaced repetition reduce cognitive load by:
  1. Breaking complex concepts into small units (flashcards)
  2. Spacing reviews to avoid re-learning (spaced rep)
  3. Allowing focused attention without searching through notes

## Core Algorithm: FSRS-Lite Scheduler

### What is FSRS?

**FSRS** = **Free Spaced Repetition Scheduler**

A modern algorithm for determining when to review flashcards, grounded in cognitive psychology and machine learning. It answers: "Given that I just reviewed a card, when should I review it again to optimize learning?"

### Why FSRS Over SM-2?

| Aspect | SM-2 | FSRS |
|--------|------|------|
| **Basis** | Empirical tuning (1990s data) | ML-calibrated on massive learner data |
| **Retention Target** | Fixed (hardcoded ~90%) | Configurable (70%-99% available) |
| **Individual Adaptation** | Limited (one EF value per card) | Full (S and D separate, personalized) |
| **Efficiency** | Baseline | 20-30% fewer reviews to target retention |
| **Stability Modeling** | Implicit in EF | Explicit (exponential decay: $e^{-t/S}$) |
| **Difficulty Adaptation** | Via EF adjustments | Independent D factor, decoupled from S |

### Core FSRS Concepts

#### 1. Stability (S) - Memory Trace Strength

**Definition:** Time constant in the forgetting curve. Higher S = stronger memory.

**Interpretation:** If a card has `S = 10 days`, it means:
- After 10 days: retrievability = e^(-10/10) = e^(-1) ≈ 0.37 (37% recall)
- After 5 days: retrievability ≈ 0.61 (61% recall)
- After 20 days: retrievability ≈ 0.14 (14% recall)

**Initial Value:** S = 3 days (new cards)
**Range:** 0.5 to 3,650 days (10 years)

**How it grows:** Each successful review increases S:
- If you recall an easy card at S = 3, next S might be 8
- If you recall hard card at S = 3, next S might be 4.5
- Cards with longer history have higher S (more retrieval events = stronger trace)

#### 2. Difficulty (D) - Inherent Material Hardness

**Definition:** How difficult is this material for learners generally? Independent of how well you know it.

**Interpretation:** D ranges from 1-10:
- D = 2: Very easy material (basic fact, everyone learns quickly)
- D = 5: Medium difficulty (average concept, requires some thought)
- D = 9: Very hard material (confusing concept, common misconceptions)

**Initial Value:** D ≈ 5 (neutral assumption)
**Range:** 1-10

**How it adapts:**
- If you consistently rate card "Easy" (quality=5): D decreases slightly
  - You: "This is trivial" → System: "OK, mark it easy for future learners too"
- If you consistently rate card "Hard" (quality=3): D increases slightly
  - You: "I keep forgetting this" → System: "OK, this is intrinsically hard"
- **Key insight:** D captures learner-independent difficulty; S captures your personal memory state

**Why separate S and D?**

Consider two scenarios:
1. **You've been learning Calculus for 6 months → S = 60 days**
2. **Your friend started learning Calculus last week → S = 2 days**
3. **Same card (fundamental theorem of calculus)**

In SM-2, these would have very different EF, but the *material* hasn't changed—only your personal learning history. FSRS keeps D constant (difficulty of material) but uses separate S (your memory state).

#### 3. Retrievability (R) - Current Recall Probability

**Definition:** Estimated probability that you'll recall this card right now.

**Formula:** $R(t) = e^{-t/S}$

Where:
- $t$ = days since last review
- $S$ = stability (days)
- $R$ = retrievability (0-1, or 0%-100%)

**Examples:**

If S = 10 days:
- $t = 0$ (just reviewed): $R = e^{0} = 1.0$ (100%)
- $t = 5$ days: $R = e^{-5/10} = 0.61$ (61%)
- $t = 10$ days: $R = e^{-1} ≈ 0.37$ (37%)
- $t = 20$ days: $R = e^{-2} ≈ 0.14$ (14%)
- $t = 30$ days: $R = e^{-3} ≈ 0.05$ (5%)

**Scheduling Strategy:** 
- Traditional: "Review in 10 days"
- FSRS: "Review when R drops to your target (e.g., 90%)"
  - To hit 90% retention: $t = -S \ln(0.9)$
  - With S=10: $t ≈ 1.05$ days
  - But if you want 75% retention: $t = -S \ln(0.75) ≈ 2.88$ days

### FSRS-Lite Algorithm: Step-by-Step

In pseudocode:

```
function applyReviewUpdate(card, quality, now):
  """
  Update card state after user reviews it
  
  card: {stability: S, difficulty: D, lapses: L, lastReviewedAt}
  quality: 0|3|4|5 ("Again"|"Hard"|"Good"|"Easy")
  now: current timestamp
  
  returns: updated card with new S, D, scheduled next review
  """
  
  // Step 1: Compute elapsed time
  R = estimateR(now - card.lastReviewedAt, card.stability)
  
  // Step 2: Apply update rules based on quality
  if quality <= 2:  // Failed ("Again")
    S_new = max(0.5, S * 0.5)          // Halve stability (memory forfeited)
    D_new = D + 0.5                     // Increase difficulty
    L_new = L + 1                       // Record lapse
  else:             // Successful (quality >= 3)
    gain = 0.18 * ((quality - 2) / 3) * (1 + (1 - R))
    S_new = S * (1 + gain)              // Increase stability
    D_new = clamp(D - 0.05 * (quality - 3), 1, 10)  // Adjust difficulty
    L_new = L                           // No lapse
  
  // Step 3: Schedule next review
  targetRetention = 0.9  // 90% recall target
  interval = -S_new * ln(targetRetention)
  nextReviewAt = now + clamp(interval, 1, 3650) days
  
  // Step 4: Record history
  card.history.append({
    ts: now,
    quality: quality,
    interval: (now - card.lastReviewedAt),
  })
  
  // Step 5: Update card
  card.stability = S_new
  card.difficulty = D_new
  card.lapses = L_new
  card.lastReviewedAt = now
  card.nextReviewAt = nextReviewAt
  
  return card
```

## Mathematical Formulation

### FSRS Retention Formula

**Fundamental Equation:**

$$ R(t) = e^{-t/S} $$

Where:
- $R(t)$ = Retrievability (probability of recall) at time $t$
- $t$ = Time since last review (in days)
- $S$ = Stability (in days) - memory strength parameter
- $e$ = Euler's number (≈ 2.71828)

**Interpretation:**
- $R$ approaches 1.0 as $t \to 0$ (just reviewed: high recall)
- $R$ approaches 0 as $t \to \infty$ (long time passed: low recall)
- $S$ controls decay rate (larger $S$ = slower decay)

### Scheduling: Inverse Retrieval Formula

**Goal:** Schedule next review such that when reviewed, $R = R_{\text{target}}$

**Solution:**

$$ t_{\text{next}} = -S_{\text{new}} \ln(R_{\text{target}}) $$

Where:
- $t_{\text{next}}$ = days until next review (interval)
- $S_{\text{new}}$ = updated stability after current review
- $R_{\text{target}}$ = desired retrievability at next review (e.g., 0.9 = 90%)
- $\ln$ = natural logarithm

**Derivation:**

Starting from $R(t) = e^{-t/S}$:
1. Set $R(t) = R_{\text{target}}$
2. $R_{\text{target}} = e^{-t/S}$
3. Take natural log: $\ln(R_{\text{target}}) = -t/S$
4. Solve for $t$: $t = -S \ln(R_{\text{target}})$

**Example:**
- If $S = 10$ days and target $R = 0.9$ (90%)
- $t = -(10) \ln(0.9) = -(10) \times (-0.1054) = 1.054$ days
- Next review: tomorrow

### Stability Update: Quality-Based Adjustment

**Successful Recall (Quality ≥ 3):**

$$ S_{\text{new}} = S \times (1 + \text{Gain}) $$

Where:

$$ \text{Gain} = 0.18 \times f(q) \times (1 + (1 - R_{\text{prev}})) $$

And:

$$ f(q) = \frac{q - 2}{3} $$

**Coefficients:**
- $0.18$ = Base learning rate (tuned empirically)
- $q$ = User quality rating (3, 4, or 5)
- $R_{\text{prev}}$ = Retrievability before this review

**Quality Mapping:**
- $q = 3$ ("Hard"): $f(q) = 1/3 ≈ 0.333$ (modest gain)
- $q = 4$ ("Good"): $f(q) = 2/3 ≈ 0.667$ (moderate gain)
- $q = 5$ ("Easy"): $f(q) = 1.0$ (maximum gain)

**Interpretation:**
The gain captures two effects:
1. **Quality effect:** Easier responses yield bigger gains
2. **Spacing effect:** Reviews when retrieval is harder (lower $R$) yield bigger gains

**Example:**

| Scenario | S | R_prev | q | Gain | S_new |
|----------|---|--------|---|------|-------|
| Easy card reviewed early | 3 | 1.0 | 5 | $0.18 \times 1 \times 1.0 = 0.18$ | 3.54 |
| Medium card reviewed when decayed | 5 | 0.4 | 4 | $0.18 \times 0.667 \times 1.6 = 0.19$ | 5.95 |
| Hard card reviewed on edge | 8 | 0.2 | 3 | $0.18 \times 0.333 \times 1.8 = 0.11$ | 8.88 |

### Difficulty Update: Response-Based Adjustment

**Formula:**

$$ D_{\text{new}} = \text{clamp}(D - 0.05 \times (q - 3), 1, 10) $$

Where:
- $D$ = Current difficulty (1-10 scale)
- $q$ = User quality (0-5, but only 3+ used here)

**Interpretation:**
- If $q = 3$ ("Hard"): $(q-3) = 0$, so $D_{\text{new}} = D$ (unchanged)
- If $q = 4$ ("Good"): $(q-3) = 1$, so $D_{\text{new}} = D - 0.05$ (slightly easier perception)
- If $q = 5$ ("Easy"): $(q-3) = 2$, so $D_{\text{new}} = D - 0.10$ (easier)

**Bounds:** $\text{clamp}(x, 1, 10)$ ensures $D$ stays in valid range $[1, 10]$

### Collection-Wide Retention Estimate

**Average Retrievability:**

$$ R_{\text{avg}} = \frac{1}{N} \sum_{i=1}^{N} e^{-(t_i / s_i)} $$

Where:
- $N$ = number of cards
- $t_i$ = days since last review of card $i$
- $s_i$ = stability of card $i$

**Example:**

Collection with 4 cards:
- Card A: last reviewed 2 days ago, $S = 5$ → $R = e^{-2/5} = 0.67$
- Card B: last reviewed 10 days ago, $S = 10$ → $R = e^{-10/10} = 0.37$
- Card C: never reviewed → $R = 1.0$ (assume stable)
- Card D: last reviewed 1 day ago, $S = 20$ → $R = e^{-1/20} = 0.95$

$$ R_{\text{avg}} = \frac{0.67 + 0.37 + 1.0 + 0.95}{4} = 0.75 \text{ (75% average retention)} $$

### Failure Mode: "Again" Quality (q = 0)

**Stability Penalty:**

$$ S_{\text{new}} = \max(0.5, S \times 0.5) $$

**Difficulty Penalty:**

$$ D_{\text{new}} = \min(10, D + 0.5) $$

**Interpretation:**
- Stability is halved (memory trace severely weakened)
- Difficulty increased (card is harder than estimated)
- Lapse counter incremented (tracks failure history)

**Example:**

$S = 20$ days (well-learned card), user rates "Again":
- $S_{\text{new}} = \max(0.5, 20 \times 0.5) = 10$ (back to half strength)
- $D_{\text{new}} = \min(10, 5 + 0.5) = 5.5$ (slightly harder)
- Lapse counter: 0 → 1
- User must re-learn card (reviews scheduled often until $S$ builds back up)

### Module 2: FSRS Scheduler Implementation

```javascript
export function applyReviewUpdate(
  card,
  quality,
  now,
  targetRetention = 0.9
) {
  const timestamp = new Date(now);
  
  // Extract current state
  let stability = card.stability || 3;
  let difficulty = card.difficulty || 5;
  let lapses = card.lapses || 0;

  // Calculate elapsed time
  let daysSince = 0;
  if (card.lastReviewedAt) {
    const lastReview = new Date(card.lastReviewedAt);
    daysSince = (timestamp - lastReview) / (1000 * 60 * 60 * 24);
  }

  // Constants (tunable)
  const BASE_LEARNING_RATE = 0.18;
  const MIN_INTERVAL = 1;
  const MAX_INTERVAL = 3650;

  let stabilityNew = stability;
  let difficultyNew = difficulty;
  let lapsesNew = lapses;

  if (quality <= 2) {
    // Failed - penalty
    stabilityNew = Math.max(0.5, stability * 0.5);
    difficultyNew = difficulty + 0.5;
    lapsesNew = lapses + 1;
  } else {
    // Successful - growth
    const R = estimateR(daysSince, stability);
    const qualityFn = (quality - 2) / 3;
    const gain = BASE_LEARNING_RATE * qualityFn * (1 + (1 - R));

    stabilityNew = stability * (1 + gain);
    difficultyNew = Math.max(
      1,
      Math.min(10, difficulty - 0.05 * (quality - 3))
    );
  }

  // Clamp difficulty
  difficultyNew = Math.max(1, Math.min(10, difficultyNew));

  // Schedule next review using inverse formula
  let intervalDays = -stabilityNew * Math.log(targetRetention);
  intervalDays = Math.max(MIN_INTERVAL, Math.min(MAX_INTERVAL, intervalDays));

  const nextReviewAt = new Date(timestamp);
  nextReviewAt.setDate(nextReviewAt.getDate() + intervalDays);

  // Build history record
  const historyEntry = {
    ts: timestamp.toISOString(),
    quality,
    interval: daysSince,
  };

  // Return updated card
  return {
    ...card,
    stability: Math.round(stabilityNew * 100) / 100,
    difficulty: Math.round(difficultyNew * 100) / 100,
    lapses: lapsesNew,
    lastReviewedAt: timestamp.toISOString(),
    nextReviewAt: nextReviewAt.toISOString(),
    history: [...(card.history || []), historyEntry],
  };
}

/**
 * Estimate current retrievability
 */
export function estimateR(daysSince, stability) {
  if (stability <= 0 || daysSince < 0) return 0;
  return Math.exp(-daysSince / stability);
}

/**
 * Get cards due for review
 */
export function getDueCards(cards, today = new Date()) {
  const refDate = new Date(today);
  refDate.setHours(0, 0, 0, 0);

  return cards
    .filter(card => {
      if (!card.nextReviewAt) return true;
      return new Date(card.nextReviewAt) <= refDate;
    })
    .sort((a, b) => {
      const aDate = a.nextReviewAt ? new Date(a.nextReviewAt) : new Date(0);
      const bDate = b.nextReviewAt ? new Date(b.nextReviewAt) : new Date(0);
      return aDate - bDate;
    });
}
```

### Failed Review Recovery

```
Scenario: Student rates a card "Again" (quality=0)

Before:
- front: "Explain the chain rule"
- stability: 15 days
- difficulty: 6
- lapses: 2
- last review: 10 days ago
- R (retriev ability): 51% (decayed, but not terrible)

Student reviews ~10 days after last review:
- R(10) = e^(-10/15) ≈ 0.51 (51% retrieval)
- Rates: "Again" (forgot, or very confused)
- quality = 0

FSRS Update:
- S_new = max(0.5, 15 * 0.5) = 7.5 (halved!)
- D_new = min(10, 6 + 0.5) = 6.5 (marked harder)
- lapses: 2 → 3
- interval = -7.5 * ln(0.9) ≈ 0.79 days
- Next review: in 19 hours (re-learn mode)

Result:
- Card pushed back to short intervals
- Must re-establish memory trace
- But system is flexible: if next review is "Good", S builds back up
- No permanent damage, no irreversible classification

Psychology:
- Helps students overcome "stuck" topics
- Removes stigma of forgetting
- Encourages active debugging (why did I forget?)
```

## Limitations & Known Issues

### Limitation 1: Quality of Computer-Generated Cards

**Problem:** LLM-generated flashcards can occasionally have:
- Ambiguous questions (multiple valid interpretations)
- Incomplete answers
- Contextual disconnect (question makes sense in conversation, not standalone)

**Current Mitigation:**
- Pre-filtering: Remove cards below quality threshold
- User feedback loop: Mark "confusing" cards for review
- Continuous LLM prompt refinement

**Example of Bad Card:**
```
Q: "So what's the key difference there?"
A: "Yeah, the algorithm handles it differently."
Problem: Question is context-dependent, answer is vague
```

**Future Solution:** Human-in-the-loop validation, card quality ratings from community use.

---

### Limitation 2: Context Window Constraints

**Problem:** 
- Extracting cards from conversations requires LLM to process all messages
- > 50,000 tokens may exceed context windows
- Long conversations lose nuance in extraction

**Example:**
- 100-message tutoring session ≈ 15,000-25,000 tokens
- Plus prompt engineering ≈ 25,000-30,000 tokens
- Within context window but loses some message-level context

**Current Mitigation:** Chunking + incremental extraction
- Divide conversation into 10-message chunks
- Generate cards per-chunk
- Deduplicate using embedding similarity

**Ideal Solution:** Fine-tuned models trained specifically on educational extraction.

---

### Limitation 3: FSRS Parameter Tuning

**Problem:**
- Base learning rate (0.18) is empirically-tuned on aggregate data
- May not be optimal for all learner populations
- Individual learners have different baseline learning speeds

**Example:**
- Gifted learner: reaches retention target faster (current params suboptimal)
- Struggling learner: needs more frequent reviews (current params too spaced)

**Current Mitigation:** Target retention parameter is configurable
- User can set to 70% (easier, fewer reviews) or 99% (harder, more reviews)
- System adapts schedule accordingly

**Research Direction:** Learn per-user learning rates after 20-30 reviews.

---

### Limitation 4: Difficulty Estimation Accuracy

**Problem:**
- Initial D (difficulty) is heuristic-based
- May mismatch actual learner-perceived difficulty
- Requires many reviews to converge to true D

**Example:**
- Expert perceives card as "easy" (easy concept for them)
- Novice perceives same card as "hard"
- System has no way to know learner expertise level initially

**Mitigation:** D adapts quickly with performance feedback (usually within 3-5 reviews)

---

### Limitation 5: Technical Debt & Scalability

**Current Issues:**
- MongoDB queries on large collections (100k+ cards) can slow down
- Embedding index rebuild latency as collection grows
- No built-in multi-language support in prompts

**Scaling Challenges:**
- One user, 50k cards: manageable
- 100k users, 50k cards each: requires database optimization (partitioning)
- Global-scale deployment: embed caching strategies, CDN for indices

## Deployment & Scaling Considerations

### Database Architecture

**Current Setup:**
```
MongoDB (Single instance)
├─ stage2_flashcards (indexed on userId, collectionId, nextReviewAt)
└─ stage2_collections
MaxScale: ~50M cards before query performance degrades
```

**Production Scaling (100M+ cards):**

```
MongoDB Cluster
├─ Shard Key: userId (partition by user)
├─ Collections:
│  ├─ flashcards (sharded)
│  ├─ reviews_history (time-series collection)
│  └─ collections (replicated across shards)
├─ Indexes:
│  ├─ {userId, nextReviewAt} for queue queries
│  ├─ {userId, collectionId, stability} for analytics
│  └─ {embedding} for RAG (separate vector DB)
└─ Backups: hourly snapshots, daily full backup
```

---

### API Server Scaling

**Current Setup:**
- Single Next.js server (node cluster with PM2)
- Handles ~100-200 concurrent users

**Production Setup:**

```
Load Balancer (Nginx)
├─ API Server 1 (Node.js)
├─ API Server 2 (Node.js)
├─ API Server 3 (Node.js)
└─ [Can scale to N servers]

Cache Layer (Redis)
├─ Cache: Recent review queues
├─ Cache: User retention stats
├─ Cache: Popular decks
└─ TTL: 5-60 minutes (depends on data freshness needs)

Job Queue (Bull + Redis)
├─ Embeddings generation (async, can be deferred)
├─ Analytics aggregation (overnight batch)
├─ Email notifications (daily digest)
└─ Cleanup (archive old review histories)
```

---

### Embedding Index Scaling

**Challenge:** Vector similarity search on 100M+ cards

**Solution: Hierarchical Index**

```
Vector Database (Weaviate or Qdrant)
├─ Partition by collectionId (shard across instances)
├─ Index type: HNSW (Hierarchical Navigable Small World)
├─ Dimension: 384 (sentence-transformers)
├─ Build time: ~2 hours for 100M cards (batch job, off-peak)
└─ Query latency: 200-400ms (acceptable for RAG)

Fallback: Approximate search
├─ If exact vector search too slow
├─ Use FAISS or Pinecone (managed service)
└─ Trade exact recall for speed
```
